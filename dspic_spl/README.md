# SPL: the dsPIC's second-stage loader

Pages 1–3 of the V2+ dsPIC (0x000800–0x001FFF). The IPL starts it at 0x000800 after every reset, while it is intact. It checks the application, gives the ESP a second to stop it, and starts it. It is the only thing that writes the application region: the ESP sends it the image over UART1 as SML class 0xF0. The application, in turn, is what writes the SPL.

Nothing in it decides anything about an update. The ESP owns every step, timeout and retry: the SPL answers one request at a time, and checks each one against what flash holds.

## Start-up

1. Clock to 40 MIPS, as the application's; the watchdog on (about 4 s); UART1 at 909091 baud, polled; the status LED.
2. Reads the IPL's info block, its own record (and checks its own CRC-32) and the application's record.
3. Chooses a mode:
   - `HELD` if the application asked for the bootloader (`ENTER_BOOTLOADER` left a request in the mailbox), which it clears;
   - `NO_APP` with no committed application record;
   - `LOOP` after 8 hand-overs without the application running 30 s (the boot-loop guard);
   - `WINDOW` otherwise.
4. Sends BOOT-STATUS, then checks the application's CRC-32 through the IPL's service (0.15 s). An image that does not match is `NO_APP`.
5. Then, polling the UART: in `WINDOW`, starts the application after 1 s unless HOLD arrives. `HELD`, `NO_APP` and `LOOP` wait for the ESP. BOOT-STATUS goes out every second while nothing else is happening.

Every hand-over counts one attempt in the mailbox. The application zeroes the count after 30 s of running (`BOOT_HEALTHY_S`).

**The hand-over** leaves the chip as reset left it: UART1, the timer and the pins back to their reset state (but UART1's TX pin, left driven high, idle, so the line to the ESP does not float while the application's C start-up runs), the PPS mappings cleared, back on FRC with the PLL settings as at reset, the watchdog off. Then `mailbox.running` is set, so traps go to the application from there on, and `GOTO 0x002000`.

## Commands

From [spl_core.c](spl_core.c), for regions `APP` (0x002000–0x028FFF, record at 0x029000) and `TEST` (0x028800–0x028F7F, record at 0x028F80):

| Request | Answer |
| --- | --- |
| STATUS | BOOT-STATUS, then ACK |
| HOLD | ACK. Mode `HELD`: no hand-over until RUN |
| ERASE | ACCEPTED, then ACK with the pages erased: the record's page first, then the rest, then each checked blank. NACK `STATE` in `WINDOW` (HOLD first), for `APP` from an unconfirmed SPL while the application is valid, for `TEST` while the application reaches the test page |
| BOOT-DATA | A chunk of 64 instructions into erased flash, read back. A repeat of a chunk already written is ACKed again. NACK `STATE` before ERASE, `CRC`, `NOT_BLANK`, `STORAGE`, `VERIFY` |
| BOOT-VERIFY | Any chunk below 0x029800, at any time |
| COMMIT | ACCEPTED, then the CRC-32 over flash checked against the ESP's (NACK `VERIFY` with the CRC-32 found), then the record's words 0–15 and the commit written and read back. A repeat of the same COMMIT is ACKed again. Ends the session: DATA and COMMIT need a new ERASE |
| RUN | ACK and the hand-over, if the image is valid. NACK `STATE` if not |
| RESET | ACK, then a software reset |

Anything else, CONFIRM included, is NACK `UNSUPPORTED`. Frames of other classes, or of the wrong length, are ignored. The SPL sends nothing but class 0xF0.

The flash routines in [spl_port.c](spl_port.c) refuse any address outside the application region and its record page before anything else, whatever the command handling decided.

## LED

| Mode | |
| --- | --- |
| `WINDOW` | Off |
| `HELD` | 4 Hz |
| `NO_APP`, `LOOP` | A double blink once a second |
| ERASE, DATA, VERIFY, COMMIT | Toggles on each answer |

## Building

An MPLAB X project for XC16, `-O1`, the small code and data models (all of the SPL's 882 bytes of RAM near, where one instruction reaches them), with each function and each object in its own section and unused ones removed. `SML_NO_MESSAGES` leaves `sml.c`'s message table out, which the linker did not drop by itself: the SPL frames and parses, but needs no table. Data initialisation on. The mailbox is `persistent` at its fixed address. The linker script confines the code to 0x000800–0x001F7F: an SPL that outgrows it does not link.

```
python3 ../tools/make_image.py spl dist/default/production/dspic_spl.production.hex -o spl.smolspl
python3 ../tools/make_image.py install --ipl ipl-0.1.0.hex --spl dist/default/production/dspic_spl.production.hex --app <app.hex> -o first.hex
```

The first is the file the application will take in an SPL update. The second programs the IPL, the SPL with its record committed and confirmed, and the application, for a PICkit. The SPL's hex alone is not bootable: it has no record.

## Testing without the ESP

[tools/pic_boot.py](../tools/pic_boot.py) does what the ESP will do, from a PC, through any serial port wired to the PIC's UART1, the ESP running a UART bridge for instance:

```
python3 pic_boot.py --port COM5 hold           # then reset the PIC: stops the window
python3 pic_boot.py --port COM5 status
python3 pic_boot.py --port COM5 update app.smolpic
python3 pic_boot.py --port COM5 test           # the test page
python3 pic_boot.py --port COM5 run
```

`update` asks a running application for the bootloader (`ENTER_BOOTLOADER`), or stops the window of a running SPL, then erases, writes, reads back, commits and runs the new image, and waits for its STAT-SYS. It needs pyserial.

## Tests

```
cd tests/host && make
```

[test_spl.c](tests/host/test_spl.c) runs the core over SML frames against a model of program memory that keeps the flash's rules and counts any write over a word not erased:
- the modes at start-up, the window to the millisecond, the boot-loop guard, a request, a mailbox not the IPL's, corrupt or uncommitted records;
- every command and every NACK, retransmissions of DATA and COMMIT, failed and wrong writes, an erase that leaves a word, frames to ignore, noise and part frames;
- the invariant (an unconfirmed SPL never erases a valid application), the test region beside a running application;
- a power cut at every flash operation of an update, each one part done, not started and complete: after it the SPL accepts the old image or the new one, whole, or none, and a new update then succeeds.

`make` also builds `spl_sim`, the core on a pipe at real time, standing in for the application after a hand-over. `pic_boot.py --sim` drives it, which is how [dspic_src/tests/tools/test_pic_boot.py](../dspic_src/tests/tools/test_pic_boot.py) tests the tool.
